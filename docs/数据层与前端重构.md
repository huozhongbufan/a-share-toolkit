## 一、实证：v3 的市场数据层没有一行真实请求

`core/market_data.py` 全文 141 行，**没有任何网络调用**。没有 `requests`、没有 `urllib`、
没有 `akshare`（虽然 `settings.py` 里写了 `DATA_SOURCE = "akshare"`，但从没被引用）。
注释自己写着「实际使用时接入 akshare 或其他数据源」。

具体是怎么造假的：

| 函数 | 声称 | 实际 |
|---|---|---|
| `get_stock_prices()` | 获取最新价格 | `info.get("default_price", 0)` —— **读配置里的默认值** |
| `get_index_prices()` | 获取指数 | **硬编码** `{"A股": 3000, "港股": 18000, "美股": 15000}` |
| `get_prev_month_sentiment()` | 上月情绪基线 | **`return 50`** |
| `build_market_data()` 里的 `rsi` | RSI 指标 | **`rsi = 50`** 写死 |
| `build_market_data()` 里的 `vol` | 波动率 | **`vol = 0.02`** 写死 |

### 最致命的两行

```python
sh_ma5  = sh * 0.99      # ← "5日均线" = 当前价 × 0.99
sh_ma20 = sh * 0.98      # ← "20日均线" = 当前价 × 0.98
...
sh_5d  = (sh - sh_ma5)  / sh_ma5  * 100    # 恒等于 +1.01%
sh_20d = (sh - sh_ma20) / sh_ma20 * 100    # 恒等于 +2.04%
sentiment = max(5, min(95, base + r5*1.5 + r20*0.5))
          = 50 + 1.01×1.5 + 2.04×0.5 = 53.5   ← **永远 53.5**
```

**v3 的核心卖点是「动态情绪阈值」。而喂给它的情绪值是一个常数 53.5。**

那套「每季度根据前 6 个月情绪涨幅自动调整阈值 ±20%」的机制，
是在对一个**永不变化的输入**做自适应。它调不出任何东西。

**AI 分析的那些「技术指标」，全都是从当前价乘一个固定系数编出来的。**

### AI 层还有静默造假的降级

`ai/engine.py` 里每个 AI 类都有一个 `_simulate()`：

```python
def analyze_market(self, market_data):
    ...
    except Exception:
        return self._simulate(md)     # ← 调用失败就返回罐头结论
```

docstring 写的是「支持 Ollama 本地部署，**自动降级到模拟模式**」。

更麻烦的是 `generate_learning_report()` 里第 369–370 行**直接调用 `self._simulate()`**
去填学习报告的正文 —— 也就是说连给用户看的学习报告，内容也是罐头的。

| v3 README 声称 | 真实含义 |
|---|---|
| 收益率 −23.22% | 在一堆常数上跑出来的数字，**不反映任何真实策略表现** |
| 预测准确率 56.5% | 模型在分析编造的指标，准确率无意义 |
| 动态阈值 +13.10pp | 阈值在对常数自适应，这个「改进」不存在 |

**我要收回之前一个论证。** 我之前说「v3 让 AI 做决策，回测 −23.22%，
所以 AI 决策不如规则决策」—— **这个引用是错的**。那个回测的输入是假的，
它证明不了 AI 决策好还是不好。

**但也仅此而已。** 在真实数据上跑之前，谁都不能说 AI 决策一定更差。

## 三、教训一句话

> **v3 的失败不是「想错了」，是「数据是假的而界面看起来像真的」。**

用户看到的是一个完整的手机端界面、三个 AI 的意见、动态阈值的调整历史 ——
**全都煞有介事，全都建立在常数上**。这比报错危险得多，因为它不会报警。

**所以下面这条要写成新系统的第一原则。**

## 四、实时数据层设计

### 4.1 先定义「实时」到什么程度

不是所有数据都需要实时。按用途分开：

| 用途 | 频率要求 | 数据 | 延迟容忍 |
|---|---|---|---|
| 信号生成（收盘后算） | 一天一次 | 前复权日 K | 分钟级 |
| **盘中止损/止盈监控** | **秒级** | 实时快照 | **越低越好** |
| 待办触发 | 事件驱动 | 实时快照 | 秒级 |
| AI 复核 | 决策时取一次 | 实时快照 + 日线 | 分钟级 |
| 全市场筛选 | 一天一次 | 全市场快照 | 分钟级 |

**关键点：盘中风控监控必须实时。** 如果只在收盘后看，止损要延迟到第二天 ——
这正是我之前标的「T+1 隔夜跳空风险」的放大版。有了 QMT 就不该再忍这个。

> ⚠️ **2026-10-19 修正：这一项不做了。**
> 按 [`我的时间安排.md`](./我的时间安排.md)，五个交易日里有四天在盘中时段有课，
> 周三 15:00 还在上微积分。**人不在电脑前，盘中监控触发了也执行不了。**
> 现在做它只会增加复杂度，不增加安全性。
>
> 这不是「做不了」，是「现阶段不该做」。等有了稳定看盘时间（或 QMT 能自动执行）
> 再回来补。在那之前，**收盘后决策 + 低频**是唯一可持续的节奏。

### 4.2 数据源（有 QMT 之后，它排第一）

| 优先级 | 源 | 能力 | 状态 |
|---|---|---|---|
| **1** | **QMT `xtdata`** | tick 快照、**推送订阅**、历史 K 线 | 待实测 |
| 2 | 腾讯 `qt.gtimg.cn` | 批量快照（60 只/请求） | ✅ 已验证 |
| 3 | 新浪 `hq.sinajs.cn` | 批量快照，需 Referer | ✅ 已验证 |

QMT 的 `xtdata` 支持 `subscribe_quote(codes, period='tick', callback=...)` ——
**服务端主动推送**，比轮询腾讯好：不用自己控频、不会被限流、没有轮询间隙。

### 4.3 架构

```
ec/feed.py
├── FeedSource（抽象基类）
│     ├── QmtFeed       xtdata，推送订阅，官方
│     ├── TencentFeed   轮询，批量 60/请求，0.12s 间隔
│     └── SinaFeed      轮询，兜底
│
├── 降级链：Qmt → Tencent → Sina
└── 统一输出 Quote，强制携带：
      source      "qmt" | "tencent" | "sina"
      as_of       数据时间戳（不是接收时间）
      latency_ms  从 as_of 到现在的毫秒数
      degraded    bool，是否用的是备源
```

### 4.4 🔴 第一原则：**降级可以，编造不行**

这条直接来自 v3 的教训。要划清界限：

| 情况 | 允许？ | 做法 |
|---|---|---|
| QMT 挂了，切腾讯 | ✅ | **界面必须显示「数据源：腾讯（降级）」** |
| 腾讯也挂了，切新浪 | ✅ | **显示「数据源：新浪（二级降级）」** |
| 全部挂掉 | ✅ | **显示「数据不可用」，拒绝出单** |
| 拿不到数据就编一个 | ❌ | **永不。这就是 v3 的死因** |
| AI 调用失败就返回罐头意见 | ❌ | **永不。改为「弃权」并显式标注** |

配套的硬规则：

1. **任何一条数据都必须带 `source` 和 `as_of`**，缺一不可
2. **`as_of` 超过阈值（盘中 60 秒 / 盘后 1 个交易日）→ 数据视为失效 → 拒绝出单**
3. **降级时工单上必须出现黄条**，不能只在日志里
4. **AI 复核失败 = 弃权 ≠ 同意**（这条我原来的设计里已经写了，继续保持）

## 五、前端重构

### v3 的现状

```python
# web/app.py 共 1127+ 行
INDEX_HTML = r"""<!DOCTYPE html>
<html lang="zh-CN">
<style>            ← 第 211 行开始，几百行 CSS
  ...
const res = await fetch('/api/analyze');   ← 第 790 行，JS 也在这里面
  ...
</style>
"""
```

**整个前端 —— HTML + CSS + JavaScript —— 是一个 Python 原始字符串。**

问题：
- 改一行样式要去 Python 文件里找
- 没有任何语法高亮/补全/校验
- 无法单独预览
- 后端和前端改同一个文件会冲突

### 新方案：分离，但仍然零构建

```
web/
├── index.html      结构
├── style.css       样式
├── app.js          逻辑（fetch JSON API）
└── （无 npm、无打包、无框架）
```

后端只做两件事：
1. 提供 JSON API（`/api/today`、`/api/tickets`、`/api/fill`...）
2. 静态文件服务（把 `web/` 目录发出去）

依然是 Python 标准库 `http.server`，**依然零依赖**，但前端可以独立编辑和预览。
需要的话还能直接用浏览器 F12 调试。

> 关于组件化：**不引入框架**。这个工作量（4~6 个页面）用原生 JS + 模板字符串
> 完全够，引入 React/Vue 会带来 npm 和构建链，破坏零依赖。
> 如果以后页面数量翻倍，再考虑。

## 六、去掉「强制一个月」，改成验收门槛

你说得对：45 天强制模拟是**因为没有账号**才定的，现在理由不成立了。

但「先验证再上真钱」这件事本身还有价值 —— 只是**不该用日历衡量**。
时间门槛是任意的（为什么是 45 天不是 10 天或 90 天？），
而事实门槛是可验证的。

**改成这样：**

```
冲刺实盘必须逐项打勾（不设天数上限）：

  □ QMT 连接建立，能读到真实持仓和资金
  □ 完成 1 笔完整闭环：下单 → 成交回报 → 自动入账 → 与券商对账一致
  □ 连续 5 个交易日数据源无中断；
    （有中断时判定：是否给出了正确告警？给了也算通过）
  □ 0 次风控绕过记录（没有任何一笔单子绕过闸门）
  □ 流水账与券商对账单 0 差异
  □ AI 复核失败时，系统正确标记为「弃权」而非「通过」
```

**全部通过就切，可能 3 天，也可能 3 周。** 不按天数算，按事实算。

这几项里有一项是专门为 v3 的教训加的：
**「AI 复核失败时正确标记为弃权」** —— 如果它悄悄算通过，一票否决。
