# AI 分工

> 当前实现在 `config.json` 的 `ai` 段和 `ec/ai_review.py`。
> 一句话：**规则决定该不该买，AI 决定有没有坑，人决定做不做。**

---

## 🔴 20261020 重大更正：之前的「三个独立模型」是假的

**这是本文档最重要的一节，因为它推翻了前面所有关于「独立复核」的结论。**

### 问题

原来的 `_run_codex()` 用 codex CLI 调 DeepSeek 和 Kimi，靠 `CODEX_HOME` 隔离。
实测发现 **codex 会忽略 `config.toml` 里的 `model_provider` 和 `base_url`，直接连 `chatgpt.com`**。

验证过程：

```
① 起一个只记录 CONNECT 目标的本地代理，用它跑 codex
   → CONNECT chatgpt.com:443
   → CONNECT ab.chatgpt.com:443
   （没有 api.deepseek.com，没有 api.moonshot.cn）

② 直接用 auth.json 里的 key 打两家 API
   deepseek  ✗ 401  "Your api key: ****P4gA is invalid"
   kimi      ✗ 401  "Invalid Authentication"
   （三份 auth.json 里是同一把 OpenAI key，sha256 完全相同）

③ 但 codex 能正确算出 7391×17=125647，耗时 11.5s、290 tokens
   → 说明它在调**别的**模型，不是配置里写的那两家
```

**结论：所谓「DeepSeek 和 Kimi 两个独立复核员」，实际上是同一个 ChatGPT 在答两次。**

### 后果

| 之前基于「独立复核」得出的结论 | 现在是否成立 |
|---|---|
| 「三个模型独立收敛于 67% 保本胜率」 | ❌ **不成立**，是两个同源模型 |
| 「Kimi 算赔率最细、DeepSeek 抓制度性风险」 | ❌ 编的分工，同一个模型 |
| 「并行独立复核是这套架构的核心」 | ⚠ 架构想法对，但**实现从来没成立过** |
| API 花费「deepseek/kimi 走订阅，¥0」 | ❌ 那次调用没记账，因为根本没走这两家 |

### 修复

改成**直连 HTTP**（`kind: "http"`），凭据从各 `config.toml` 的
`experimental_bearer_token` 读取（`auth.json` 里那把是错的）。

| 模型 | base_url | model | 关键参数 | 实测 |
|---|---|---|---|---|
| deepseek | `api.deepseek.com/v1` | `deepseek-flash` | — | 4~8s，1400~2000 tokens |
| kimi | `api.moonshot.cn/v1` | `kimi-k3` | **`temperature` 必须 = 1**，`max_tokens ≥ 8000` | 80~99s，3400~4400 tokens |
| claude | Claude Code | — | — | 独立验证过，是真的 |

### 修复后的证明

同一个问题（sh512000，443.70 元，往返 2.29%）：

```
deepseek  7.6s  reject  confidence 0.84  「净盈亏比仅约1.04:1」
kimi     98.5s  reject  confidence 0.60  「净盈亏比约1.04:1；保本胜率需超过49%」
```

**核心数字一致，但把握度和侧重点不同** —— 这才是两个真正独立的模型。
同一个 ChatGPT 答两次会给出几乎相同的措辞和置信度。

### 踩过的三个坑

1. **`auth.json` 里的 key 是错的。** 三份都是同一把 OpenAI key，对两家 API 都 401。
   真正的凭据在 `config.toml` 的 `experimental_bearer_token`。
2. **`kimi-k3` 只接受 `temperature=1`。** 传 0.2 直接 400。
3. **思考型模型要留够 `max_tokens`。** kimi-k3 的 reasoning token 也算在里面，
   3000 会把 JSON 拦腰截断。截断时 `finish_reason=length`，
   现在会明确报「token 不够」，不再含糊地报成 JSON 解析失败。

### 这个教训值多少

**比省下的 API 钱重要得多。** 如果没查出来，你会一直以为自己在做
「三个模型交叉验证」，实际上是一个模型的回音室——**这恰恰是当初批评 v3 时说的那个毛病**。

**「AI 复核」的价值完全建立在「独立」两个字上。不独立，它就只是安慰剂。**

### 最终分工（20261020 定稿）

| 层 | 模型 | 干什么 | 参与决策？ |
|---|---|---|---|
| **决策** | deepseek（直连） | 独立复核，¥0.002/次 | ✅ 有否决权 |
| **决策** | kimi（直连） | 独立复核，¥0.02/次 | ✅ 有否决权 |
| **决策** | claude（CLI） | 独立复核，¥1.29/次 | ✅ 有否决权（金额 ≥¥645 才叫） |
| **检索** | **r1（deepseek-r1:8b，本地）** | 从 7696 只代码表里找标的 | ❌ **只找文件，不投票** |
| 检索 | qwen2.5:7b（本地） | 同上，r1 失败时降级 | ❌ |
| 检索 | glm4:9b（本地） | 同上，再降级 | ❌ |

**为什么把 r1 从决策层踢出去：** 实测它在复核任务上给出
「把止损放宽到 8-10%」——在 ¥500 本金下这是**会加大亏损**的建议（止损越宽，单笔亏得越多）。
而且它漏掉了两个 API 模型都抓到的核心问题（费用吃掉盈亏比）。

**但它在检索上反而更强：**

| | qwen2.5:7b | **deepseek-r1:8b** |
|---|---|---|
| 查询「防守型」的扩展 | `[红利, 银行, 黄金]` | **`[红利, 银行, 黄金, 低波, 防御]`** |
| 挑出的标的 | 泛红利 ETF | **全是「红利低波」系列** |
| 耗时 | 7.5s | 51.4s |

**慢 7 倍，但准确率高得多。** 所以 r1 排在检索链第一位，失败时才降级到 qwen。

> 一个 8B 模型的能力是有形状的：**能做「找」，不能做「判」**。
> 让它找文件，别让它签字。

**两个必须记住的开关（实测相反）：**

| 模型 | `think` | `num_predict` | 现象 |
|---|---|---|---|
| qwen3.5:4b | **False** | 600 | True 会把 token 全烧在思考上，返回空 |
| deepseek-r1:8b | **False** | **≥1600** | True 时给 1600 甚至 2400 都返回空（`done_reason=length`） |

**r1 的特殊之处：`format: "json"` + `think: False` + 大 token 才有输出。**

### 给小模型装上实时数据（`run.py ask`）

GitHub 上找过三个现成方案，**都不该用**：

| 项目 | ★ | License | 硬伤 |
|---|---|---|---|
| ArvinLovegood/go-stock | 7,881 | **GPL-3.0** | 传染性许可，代码不能拿 |
| Guling-Pro/guling-trader | 21 | **AGPL-3.0** | 传染性最强，而且**实盘下单**，危险 |
| a-stock-mcp-server | — | MIT ✓ | 底层是 AKShare，README 自己写「**数据延迟 15-20 分钟**」 |

**最后一条是关键**：`a-stock-mcp-server` 用 AKShare，而 AKShare 走东财，
本项目实测过会被封 IP。而且它承认有 15-20 分钟延迟 —— 那正是要避免的老数据。

本项目 `quotes.py` 走腾讯 `qt.gtimg.cn`，`ts` 精确到秒。所以不引入任何依赖，
直接把已有数据层包装成 ollama 的 `tools`：

```bash
python run.py ask "农业银行、沪深300ETF现在多少钱？"
```

```
[轮 1] tool_calls=1
  调用 get_quote(['农业银行', '沪深300ETF'])
[轮 2] tool_calls=0

答案：
  农业银行最新价为7.33元，下跌了2.14%。
  沪深300ETF华泰柏瑞最新价为4.245元，上涨了0.12%。

耗时 3.7s
  · sh601288 农业银行 7.33 -2.14% 成交 150,915万  2026-10-20 10:48:48 (3秒前)
  · sh510300 沪深300ETF华泰柏瑞 4.245 +0.12% 成交 189,609万  2026-10-20 10:48:49 (3秒前)
```

**为什么不用 MCP 协议：** ollama 不原生支持 MCP，要额外写桥接。
它从 v0.4 起原生支持 OpenAI 风格的 `tools`，直接给函数定义就能用 ——
少一层中间件，少一处会坏的地方。

#### 最关键的设计：让模型传「名字」，别让它猜代码

第一版工具要求模型自己写 `["sh601288", "sz159841"]`，实测直接翻车：

```
qwen2.5:7b  → 传了 sh601280 / 159860     （代码错了两位）
deepseek-r1 → 没调工具，还编了个 601169  （更糟）
```

7B 模型记不住 7696 个代码。改成传名字、内部用同花顺表转代码之后就对了。

> **小模型的工具参数必须是自然语言，不能要求它做代码映射。**

#### 第二个坑：紧凑时间戳会被误判成「过时」

工具最初返回 `data_time: "20261020104857"`，模型回答「数据时间为 20261020104857，
**可能已经过时**」—— 而那一刻正是当下。

修法：转成可读格式 + 附一个 `data_age_sec`，并在 SYSTEM 里明确
「小于 300 秒就是实时，不要说它过时」。

> **给模型的每个字段都要考虑「它会不会读错」，而不是「格式是否紧凑」。**

### 顺带修掉的一个 bug

`llm_rerank` 原来的成功判定是 `invalid == 0 and bool(hits)` ——
**模型给了一个代码缺失的 pick，整批正确结果全被丢掉。**
r1 正好有这个毛病（5 个候选里 1 个没写 code，剩下 4 个全对，却被判为失败）。
改成「有有效结果就算成功」，无效个数单独返回给上层提示。

## 三、第 1 层：本地小模型做同花顺检索（实测）

```bash
python run.py find 防守型
python run.py find 白酒类ETF
python run.py find 深发展A --renames     # 用旧名查现在的代码
```

实测四组：

| 查询 | 结果 | 说明 |
|---|---|---|
| `茅台` | sh600519 贵州茅台 | 名称直接命中 |
| `白酒类ETF` | sz161725 白酒基金LOF | 名称直接命中（它是 LOF 不是 ETF，类别按组处理才对） |
| `光伏` | 5 只光伏ETF | 名称直接命中 |
| **`防守型`** | 红利低波 ETF 系列 | **名称里没有「防守型」，模型扩展成「红利/银行/低波」再搜** —— 这是纯规则做不到的 |
| `深发展A --renames` | sz000001 深发展A → 平安银行 | 查同花顺的历史名称表。**任何在线接口都不会告诉你这个** |

### 三条硬规则

1. **模型不产生代码，只从本地候选里挑。** 返回的代码若不在候选集里，直接丢弃。
   同花顺的表是唯一事实来源 —— 编造代码在这个系统里零容忍。
2. **每个结果标记 `命中` / `推断`。** 「命中」= 名称里真的有查询词；
   「推断」= 模型按语义挑的，界面上必须能区分。因为 7B 模型有个通病：
   **宁可凑数也不返回空。**
3. **模型不可用时退回确定性预筛，并且明说「这不是模型的选择」。**

### 踩过的坑（都写在代码注释里）

| 坑 | 现象 | 修法 |
|---|---|---|
| 类别词当关键词 | "ETF" 出现在所有 ETF 名字里，60 个候选全是 ETF，模型在噪声里硬凑出「金融地产ETF」「医药ETF」 | 类别词只用于过滤，不进关键词 |
| 类别过滤太硬 | 「白酒类ETF」→ 过滤成 ETF → 白酒基金是 LOF → **0 结果** | 类别按组：ETF/LOF/基金算一组 |
| 3 字词组不拆 | 「白酒类」整串匹配不到「白酒基金」 | 3 字词组额外产出 2 字窗口 |
| 模型爱凑数 | 候选全是噪声时，它仍返回 3 条并编理由 | 加 `matched` 标记 + 预筛只放实质命中 |

## 四、三个评审员各擅长什么（实测出来的，不是猜的）一次真实复核，两个模型抓到了**不同的**漏洞：

| 模型 | 实测表现 | 单次成本 | 耗时 |
|---|---|---|---|
| **DeepSeek** | 抓制度性和结构性风险。原话：「T+1 标的当天根本执行不了止损，隔夜跳空穿透止损后单笔亏损可放大到本金的 5%~9%」 | ≈ ¥0.005 | ~40s |
| **Kimi** | 算赔率和胜率最细。原话：「止盈实现时净赚约 10.5 元、止损实现时净亏约 23.7 元，需要约 69% 胜率才能打平」 | ≈ ¥0.025 | ~60s |
| **Claude** | 推理最深，会自己把算术做穿。原话：「把 1.45:1 的表面盈亏比压成 1:5.7（净 +3.43 vs 净 −19.57），打平需 85.1% 胜率，按 50% 胜率每笔期望 −8.07 元」 | **≈ ¥1.4** | ~36s |

**Claude 贵 50 倍，但深得多。** 它算出的「打平需 85.1% 胜率」比我们自己的风控闸门还细。
后来那条闸门（`打平所需胜率`）就是被这类意见催出来的。

**但它只在真有候选要复核时才会被调用** —— 现在费用闸门几乎天天拦，
一年实际也就调用几十次，总成本几十块。

## 三、为什么必须并行，不能串行

v3 是串行的：DeepSeek 分析 → Kimi 看 DS 的结论做风控 → 千问看前两个做决策。

```
  串行：  A ──结论──→ B ──结论──→ C ──→ 决策
          （B 看到 A 的结论，被锚定；C 看到两份已趋同的意见）
          三票看起来像三重保险，实际是一票放大三次

  并行：  A ─┐
          B ─┼─→ 聚合
          C ─┘
          （三个都看同一份原始数据，谁都看不见别人的结论）
```

> ⚠️ 这里我要收回之前一个说法：v3 的回测 **−23.22% 不能**用来证明「串行不好」，
> 因为它的市场数据是编的（见 `v3复盘.md`）。站得住的只剩**架构论证**，不是实证。
> 在真实数据上跑之前，谁都不能说 AI 决策一定更差。

## 四、聚合规则

```
任何一个模型：
    强否决（verdict=reject 且 confidence ≥ 0.8）  → 拦截，不出单
    赞成或谨慎（approve / caution）                → 计一票赞成
    超时 / 报错 / 拒答                              → 弃权，**不计入赞成**

全部结果：
    赞成数 ≥ min_approvals (默认 1)   → 放行，进「待确认」
    赞成数 <  min_approvals           → 拦截
    全部弃权                          → status=unavailable，工单标「这不是复核通过，
                                        只是没有额外信息」，交给人决定
```

**关键：弃权 ≠ 同意。** 这条是硬规则，因为静默把失败当通过是 v3 的死因之一。

## 六、还没定的一件事

三个评审员现在是**同角色并联**：都回答「这个建议有什么风险」。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 同角色并联**（当前） | 三个答同一个问题 | 投票有意义，分歧就是信号 | 同质化，三票的独立性打折 |
| **B 不同视角** | 风险审查 / 数学审查 / 反方辩论 | 覆盖互补 | 不是投票，是清单 |
| **C 混合** | 两个同角色投票 + 一个专职反方辩论 | 兼顾 | 稍复杂，多一次调用 |

实测看，A 已经能产出互补的信息（DeepSeek 抓制度风险、Kimi 算赔率）。
所以**可以先跑 A，等积累几十次真实复核记录再决定要不要加 C**。

加 C 的做法很简单：给某个模型单独一个 system prompt，任务是
「构造这笔交易为什么是错的论证」，而不是泛泛地「找风险」。

## 七、一次真实的三模型复核（2026-10-19 实测）

标的 `sh512000` 券商ETF，900 份 / 441.00 元，往返费用 10.18 元 = 2.31%。

### 三个模型独立收敛到同一个结论

| 模型 | 结论 | 把握 | 耗时 | 成本 |
|---|---|---|---|---|
| deepseek | reject | 90% | 15s | ¥0 |
| kimi | reject | 70% | **189s** | ¥0 |
| claude | reject | 88% | 36s | ¥1.29 |
| **合计** | | | **240s** | **¥1.29** |

**它们各自独立算出了同一组数字：**

- **deepseek**：「扣除费用后赔率约为 0.49:1，需要 67% 胜率才能打平，
  而策略本身给出的理由是零证据（打分 0.0、20 日动量为负、价格在 MA60 下方）；
  并且 T+1 之下，3.47% 的止损挡不住隔夜跳空。」
- **kimi**：「最低佣金把往返成本抬到本笔的 2.31%，使净盈亏比倒挂：
  止损净亏约 25.3 元、止盈净赚仅约 12.5 元，需要约 67% 的胜率。」
- **claude**：「把 1.45:1 的表面盈亏比压成 1:5.7，打平需 67% 胜率，
  而按 2.0ATR 止损 / 3.0ATR 止盈的无漂移随机游走只有约 40%。」

**三个独立模型算出的打平胜率完全一致：67%。** 这不是巧合，是费用结构决定的。

### 两个模型提了同一处规则建议

- deepseek：「把『打平所需胜率』从通过项改成硬否决」
- claude：「把『打平所需胜率』从通过项改成硬否决：胜率 ≥50% 即拒绝。
  仅此一处改动即可挡下本笔交易，不涉及加仓、不放宽任何现有阈值。」

**这条规则我早就有了**（`risk.max_required_win_rate = 0.55`），
而且它本来就会拦下这笔（66.9% > 55%）。这次没拦是因为跑的是 `--demo`，
demo 把这条闸门从 55% 放宽到 95% 了。

**也就是说：三个 AI 独立得出了我的规则引擎已经写好的结论。** 这算是对规则的一次验证。

### Claude 抓到一个真实缺陷（已修）

> 「建议书写的 12.50 / 25.30 与重算差 0.18 元，约为单边滑点 0.09 的两倍，
> 费用算术自相矛盾。」

**不是矛盾，是我简报里没说明费用含滑点。** 模型重算时对不上就判定为矛盾。
已修：简报现在明确写出费用明细 ——

```
费用明细(单边): 佣金 5.0 元(最低佣金已触发) ＋ 滑点 0.09 元(2.0 bp)＝ 5.09 元。
**上述所有费用数字均已含滑点。**
```

这也是个通用教训：**给模型的数据要能自洽地复算出来，否则它会把你当成算错了。**

   要么让它只做单一视角（少写点废话）。
2. **deepseek 和 kimi 走 codex 通道，不报告成本**（`cost_usd=0`），订阅制已经付过。

### Claude 接入踩的三个坑（记下来免得重踩）

1. **`--json-schema` 只吃内联 JSON**，传文件路径会报
   `Unexpected identifier "C"`（把盘符 `C:` 当成了 JSON 标识符）。
2. **`--output-format json` 返回的是包装信封**，结论在 `result` 字段里，
   而且 `result` 本身是**字符串形式的 JSON**，要 `json.loads` 两次。
3. **开销压不下去**：无论 `--allowed-tools ''` 还是 `--disallowed-tools`，
   input 都在 27k~35k tokens，其中绝大部分是 Claude Code 自己的系统提示词。
   实测 $0.20/次。想真正做到 ¥0.01 级别只能用 Anthropic 原生 API（需要单独的 key）。
